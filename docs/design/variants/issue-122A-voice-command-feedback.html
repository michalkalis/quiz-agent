Issue #122 Track A —
Voice command recognition feedback

Today the app gives zero visual confirmation that a spoken command was heard: CmdListenBar renders the identical static bar before, during and after a command fires, and an unmatched utterance produces nothing at all but a sampled Sentry log. The gap the founder feels while driving is the latency window between "recognized" and "the action visibly lands" — so he repeats himself.

Below are three genuinely different ways to close that window, mocked on the real quiz screen with the real dark-mode tokens and the real Slovak command copy. Every variant shows the same three states side by side, with the rest of the screen dimmed so the feedback element is the only thing competing for attention. Pick one — it then goes to Pencil (component s49sd) and only afterwards into code.

What every variant answers the same way

These six questions come from the issue's "Scope of a fix". Five of them have one right answer regardless of which visual direction wins — locking them here keeps the variant choice a purely visual one.

QuestionAnswer, and why
Colour semantics for "heard you, didn't understand" Amber #F59E0B (the existing warning token), never error #FF4444. Nothing failed — the app is working correctly, it just did not match a command. Red at 90 km/h reads as a crash; amber reads as "say it again". Teal keeps its single meaning: the listener is live.
Does the recognized state name the command back? Yes — and it is free. VoiceCommandLexicon.spokenWord(_:language:) already returns the localized canonical form ("štart", "preskoč", "zopakuj"), so naming the command costs zero new strings. It doubles as the founder's recognition-quality check. (Variant C is the deliberate exception — it names nothing.)
How long does each transient state persist? Matched: min 600 ms, max 2.0 s, whichever the screen change allows — the min-display floor is what stops a <200 ms action from flashing; the max is what stops it from lying about a stuck network call. Not matched: fixed 1.2 s, no min/max coupling since nothing is pending.
Does "not recognized" fire on every unmatched utterance? No — throttled. Fire only on a final transcript that still has ≥1 non-filler token after fillerWords stripping, at most once per 4 s, and never twice in a row for the same transcript. The mic is open through ordinary passenger conversation; an indicator that lights on every Slovak sentence is itself the distraction.
Does the recognized state suppress the listener? No — presentation-only (recommended). The complaint is "I don't know if it heard me", not "it fired twice". Disarming the window would drop a legitimate follow-up command and pushes the change into VoiceCommandCoordinator+Listening.swift. Keep it cosmetic + the existing .commandAck earcon. Variant B is the one direction where suppression is arguably worth it.
Does the bar's caption get localized? Yes. "LISTENING FOR COMMANDS" is hardcoded English and stays English in Slovak mode — a real gap. It becomes a localized string keyed off CommandEngineSelection.current.commandLanguage (the command language, not the app language — same rule hint(on:language:) already follows). Slovak: POČÚVAM PRÍKAZY. All mockups below show that fix in place.

Glanceability while driving

Medium

The signal sits where the eye has already learned to look, but the differentiator is a 10 pt mono caption plus a tint shift inside a 62 pt box. From a phone mount in peripheral vision you reliably get teal vs. amber and the presence or absence of motion — the words themselves need a real glance.

Distraction risk

Lowest

Nothing appears, nothing overlaps the question, and the box height is identical in all three states, so there is zero layout jump on a bumpy road. It is the only variant a driver can completely ignore without losing information elsewhere on the screen.

Implementation surface

Smallest

CommandCapturePhase gains .heard(VoiceCommand) and .unmatched; CmdListenBar gains two style branches; the two existing call sites (+Utterance.swift:330, +Routing.swift:98) get wired to a min-display timer. No new view, no overlay, no z-order, no new copy beyond three strings. Automatically inherits every screen that already renders the bar.

Variant-specific answers:
  • Morph in place — no separate overlay, no layout jump by construction.
  • Names the command (ŠTART), free via spokenWord.
  • Listener stays armed; the state is presentation-only next to the existing .commandAck earcon.
  • Primary peripheral signal = colour + motion presence; the text is the secondary, confirming layer.
B

Command echo

The bar is left exactly as it is. A transient card rises above it for ~1.2 s and echoes back, in display type, the word the recognizer matched — or, when nothing matched, what it actually heard.

Transient overlay · loudest · most informative

This is the only variant that shows the raw transcript — enormous diagnostic value for tuning the lexicon, but it is a reading task in a moving car, so it should be gated behind a setting (default off) with the plain "?" card shipping by default.

Glanceability while driving

Highest (matched)

Anton 34 on a lit teal card is resolvable in roughly the length of a single glance, and it is the only design that answers "what did it hear" rather than just "did it hear something". The unmatched state inverts that: reading a transcript is the least glanceable thing on this page.

Distraction risk

Highest

Something new appearing over the question is exactly the motion pattern that pulls foveal attention off the road. The 4-second throttle becomes load-bearing rather than nice-to-have, and the transcript echo needs its own opt-in. This is also the one variant where briefly suppressing the listener is defensible, so the card is not immediately replaced by a second card.

Implementation surface

Largest

A new overlay component plus presentation-timer state on the coordinator, z-order and safe-area handling on every surface that hosts the bar (question, MCQ, the confirmation sheet, result), and min/max-display coordination so a card never outlives the screen change that follows it. Exposing the raw transcript also puts recognizer output on screen for the first time.

Variant-specific answers:
  • Separate transient overlay — the bar itself is never touched; the resting screen keeps its current density.
  • Names the command and optionally the raw transcript on a miss.
  • Recommended to suppress the listener for the card's lifetime, so the feedback matches what the app will act on.
  • Primary signal = size and type; the card is deliberately loud, which is its strength and its risk.
C

Ambient glow

No new words at all. The whole bottom third of the screen washes teal and a light sweeps across the full width when a command lands; a slow amber breath when nothing matched. Designed to be read by peripheral vision, not by eyes.

State 3 · no match One slow amber breath Half the amplitude of the matched wash, one 2.2 s fade in-and-out instead of a directional sweep, and the animated dots stop. The absence of the sweep is what distinguishes it — a driver learns "moving light = it acted, still light = it didn't".

Glanceability while driving

Highest peripherally

Large-area colour and lateral motion are precisely what peripheral vision resolves well, so this works when the phone is at the edge of the visual field in a mount — no foveal glance needed at all. The cost: it conveys that something registered, never what, so it does not double as a recognition-quality check.

Distraction risk

Low to medium

Nothing to read and no layout change, but a large glowing area in a dark cabin at night is a strong attention magnet, and it is the variant most damaged by a mis-throttled no-match (it would read as strobing). Amplitude must stay low, and accessibilityReduceMotion needs a static-tint fallback with no sweep.

Implementation surface

Medium

Zero new copy and zero localization work — the single cheapest variant on the string side. But it lives at the screen-container level rather than inside one component, so it needs a modifier on QuestionView's bottom stack (and later on each other host), plus a reduce-motion branch and care that the glow never bleeds into the answer-confirmation sheet's own chrome.

Variant-specific answers:
  • Neither morph nor overlay — a background layer, so no layout can jump by definition.
  • Does not name the command — deliberately. Motion and size are the entire signal.
  • Listener stays armed; purely presentational.
  • Matched vs. not-matched is carried by hue + whether the light moves, which survives a glance the words would not.
