## Context

- D24 (final form): debug surface = **rating only** — 10 separate buttons (1–10, higher = better) + optional audio justification (transcribed, stored with the rating). No answering questions, no approval queue in the app. Available only in TestFlight builds; removed before the App Store version.
- D20: today's in-app rating plumbing (`QuizViewModel.rateQuestion` → `NetworkService.rateQuestion` → quiz-agent `/rate`, 1–5 SQLite) has **zero UI call sites** and nothing reads it. This issue supersedes that path for founder ratings — new ratings go to the #154 canonical store (1–10), not to `ratings.db`.
- Existing dictation pattern to reuse: the #109 beta-feedback `FeedbackViewModel` / `FeedbackVoiceServices` bundle (shared `AudioService` + ElevenLabs STT, quiz-recording guard, 120s cap, permission fallback to typing).

## Agent Brief — 2026-08-14

> *This was generated by AI during triage.*

**Category:** enhancement
**Summary:** TestFlight-gated rating affordance during a quiz: button opens a panel with 10 score buttons + optional dictated justification; submits to the #154 ratings API with the current question's UUID.

**Current behavior:**
No rating UI exists in the app. Founder impressions during play are lost or retyped later into web rating rounds.

**Desired behavior:**
- A small rating button appears on both the question screen and the result screen, only when the build is a TestFlight build (runtime App Store receipt sandbox detection; also visible in `#if DEBUG` builds for development). App Store builds show nothing — plus keep a pre-GA removal reminder in TODO per D24's "remove before App Store".
- Tapping opens a panel (sheet): the 10 buttons 1–10 (higher = better), an optional justification — mic button starts dictation via the shared audio/STT services (same guard pattern as beta feedback: never while the quiz itself is recording; nil STT service → text field only), live transcript shown and editable as text.
- Submitting posts to the #154 quiz-pack-api ratings endpoint: question UUID = the currently displayed question's `id`, rater identity (founder), score, justification text, source `in-app`; authorized with the user's bearer JWT. Non-blocking: fire-and-forget with a brief confirmation; failure surfaces a non-intrusive error and does not disturb quiz state.
- Rating-only: the panel never reveals answers, never approves/rejects questions, never affects quiz flow, scoring, or TTS. Re-rating the same question replaces the founder's previous score (API semantics from #154).

**Key interfaces / call paths:**
- Question/result screen views — the entry button; quiz state machine untouched.
- A new small ViewModel following the `FeedbackViewModel` dictation pattern (`FeedbackVoiceServices`-style construction from `AppState` shared services).
- `NetworkService` — new method targeting the quiz-pack-api base URL (already used for pack orders), not quiz-agent.
- `Question.id` via `QuizViewModel.currentQuestion` — the stable identifier; result screen must rate the question just answered, not a stale one.
- TestFlight detection helper (receipt `sandboxReceipt`) — one shared utility, unit-testable via injection.

**Acceptance:** see the top-level `## Acceptance` block.

**Out of scope:**
- The old quiz-agent `/rate` 1–5 path — leave as-is (do not extend, do not delete here).
- Multi-rater web (#154 UI), backfill (#156), any generation-side reading of ratings.
- Player-facing rating for real users (this is a founder/TF tool, D29).
- Answer-flow or design changes to question/result screens beyond the one affordance.

**Suggested feedback loop:**
iOS unit tests (ViewModel: score selection, dictation guard, submit payload, TF-gating predicate via injected detector) + one simulator pass with the panel force-enabled (Debug) against a local quiz-pack-api; `swiftformat` auto-runs.

## Implementation notes (2026-08-14)

- Entry point is an optional `QuestionRatingEntry` value passed down from `ContentView`, **not** an `@EnvironmentObject` lookup: `QuestionView`/`ResultView` are hosted bare in dozens of unit tests and an environment lookup would crash all of them. Default `nil` = no affordance, which is also what an App Store build renders.
- The rating client is a separate `QuestionRatingService` actor (pack-api host + bearer via `AuthService.sendAuthorized`), mirroring `PackOrderService`, rather than a method on `NetworkService` (which targets the quiz-agent host).
- `display_name` is deliberately never sent: a hardcoded "founder" would mislabel other TestFlight raters, and identity is the JWT subject anyway.
- The chip is an overlay in the top-trailing chrome row, with a PER-SCREEN trailing inset (voice question 64, MCQ question 96, result 108) because what sits at that edge differs (settings gear / merged counter / nav counter). A single shared inset clipped the question counter — caught by a simulator pass, fixed in `f88291b9`. No Pencil round — temporary debug surface.
- **Open residual:** the corrected insets are geometry estimates; the follow-up simulator screenshot pass had not reported back when the run ended, so the fixed placement is not visually confirmed. If the founder sees a clash, it is a one-number change per screen at the `.questionRatingEntry(…)` call sites.
