## Resolved design decisions

**DD1 — Serving gate = a materialized `approved_languages` array column on `questions`, filtered with a new `$contains` operator; unknown filter keys become fail-loud.**
The pgvector filter surface is flat single-column equality with no joins (`pgvector_client.py:113-134`), so a join to the translations table is out; a post-retrieval filter is also out because it would shrink the candidate pool *after* semantic ranking (silently biasing selection and starving `_handle_no_candidates`). Per-language boolean columns are rejected as second-order poison — 9 languages is 9 migrations. Decision: `questions.approved_languages TEXT[] NOT NULL DEFAULT '{}'` with a GIN index, written **only** by the pipeline in the same transaction that flips a translation to `approved` (or removes a language on rejection/retranslation); the translations table stays the system of record and the column is a derived retrieval index. `_build_where` gains one operator (`$contains` → Postgres `@>`), and `_build_metadata_filters` adds `{"approved_languages": {"$contains": lang}}` only when `session.language != "en"`, mirroring the existing `language_dependent` guard (`question_retriever.py:262-263`). The fallback ladder needs no change — every fallback reuses the primary dict and relaxes only `difficulty` (`question_retriever.py:334-376`), so the gate survives all three rungs; it must never become relaxable. The gate's *other* consumer is not a fallback and does need changing: `/start`'s exhaustion accounting counts the corpus globally (`quiz.py:124-126`) and must apply the same language gate — DD16.
*Drift control — two legs, both in `reconcile`.* (1) **Consistency:** recompute the column from the translations table and exit non-zero on any mismatch; a test asserts column ⇔ table agreement. (2) **Staleness (DD3's `source_hash`):** recompute each approved row's hash from the *current* English question and compare it to the stored `source_hash`; on mismatch **demote in one transaction** — `status` `approved → stale`, language removed from that question's `approved_languages` — and report the affected qids (`qid, language, old_hash, new_hash`) with a non-zero exit. `stale` is a distinct status from `pending` so `report --coverage` can tell "never translated" from "invalidated by a source edit"; re-translation of a `stale` row is ordinary `submit` work. A consistency-only reconcile would pass happily on a stale row, since the column and the table agree with each other and are both wrong about the English text.
*Index honesty (do not overclaim):* the pre-filter is exact only while the planner seq-scans. `search()` emits `WHERE … ORDER BY embedding <=> q LIMIT n` (`pgvector_client.py:270-290`) and the only vector index is `ix_questions_embedding_ivfflat` (`lists = 100`, `1c5e0fa7b3d4…:256-257`); on an **ivfflat index scan the filter is applied after approximate candidate selection**, so a selective language filter can lose recall. At the current corpus scale (hundreds of rows) the planner will not choose the index, so today the filter is exact — this is a property of the corpus size, not of the design. Verify with `EXPLAIN ANALYZE` on a real SK filter at cutover and revisit (per-language partial index, or a raised `ivfflat.probes`) if the corpus ever reaches index-scan scale.
*Pack path:* the new key goes **only** into the normal branch (`:251-267`). The pack branch returns early at `:234-241` with `{pack_id, type}` (+ `language_dependent`) and is untouched, so the gate cannot empty a paid bundle; the pack fallback already returns `[]` (`:331-332`). What a pack question then serves in a non-EN session is settled by DD15.

Every filter key in use is a real column (`question_retriever.py:208-269`; quiz-pack-api's `filters` dicts in `generation/storage.py` are filtered in Python and never reach this store), so the "best-effort constraint" contract has no live consumer. *Who notices an edit — the write path, with reconcile as backstop.* Cheapest honest option: **demote inline in `PgvectorQuestionStore.upsert` (`pgvector_client.py:185`)** — the shared write path used by `POST /questions/backfill-sources` (`admin.py:331`), `POST /questions/review-status` (`:375`), `POST /questions/set-category` (`:425`) and quiz-pack-api's persist stage. Rejected: import-time *flagging only* (leaves the stale translation serving until someone reads a report) and a scheduled reconcile (a serving-correctness invariant should not depend on a cron nobody owns).
`question_translation_corrections` (append-only): `translation_id`, `field`, `before`, `after`, `category` (MQM-Quiz), `note`, `source`, `created_at`. **DD4 — Clean cut on serving, no dual-path flag; ordering is the safety mechanism.**
A `serve legacy vs approved` toggle would keep alive the exact failure mode locked decision 2 kills (unverified translation reaching a player) behind a switch nobody would deliberately flip back, and it doubles the test matrix on the hot path. Prod has no real users (founder only), so the rollback is the cheap one: revert the quiz-agent deploy; the migration is additive and stays. Safety comes from **sequence**, not from a flag: (1) table + runner + gate code shipped with the gate inert (no `approved_languages` written, EN unaffected); (2) arm test → founder model verdict; (3) SK corpus translated + verified + reviewed to a coverage threshold; (4) only then flip `_build_metadata_filters` on and delete the serve-time path. A pre-cutover coverage check in the runner (`report --coverage`) is the gate on step 4 — insufficient coverage is an operational precondition, never a runtime English fallback.
*Migrate before deploy — stated, not assumed (C2).* Step 1 is **not** "deploy code, then migrate". `questions_table` in `packages/shared` is an explicit column declaration read by both services, and every read goes through it (`select(questions_table)`, `pgvector_client.py:270-290`), so code whose declaration lists `approved_languages` against a database that lacks the column 500s on **every** retrieval, EN included. Ordering, per the repo's migrate-before-deploy convention (`project_backend_arch_review_2026_07_18`, run from the repo root): apply the additive alembic migration to `quiz_pack_staging` → deploy staging → founder gate → apply to the prod logical DB → deploy `quiz-agent-api` + `quiz-pack-api`. The migration is additive with a `DEFAULT '{}'`, so the *old* code keeps working against the *new* schema — which is exactly what makes this order the safe one and the reverse order an outage.
*The step-4 gate, defined (a global percentage is the wrong quantity).* Starvation is a per-**(category × difficulty)** property, because the primary filter pins both together (`question_retriever.py:251-267`) — a healthy global number can coexist with a Slovak `food-everyday`/`easy` session that serves nothing. `report --coverage --language sk` therefore counts **serving-eligible rows per cell**: eligible = `pack_id IS NULL AND review_status = 'approved' AND language_dependent = false`, counted for EN and for the target (`approved_languages @> {lang}`) across the 6 `CATEGORY_TAXONOMY` values × `easy|medium|hard` = 18 cells (no such crosstab exists today — recon §10 — so the report computes it). Three bars, all required:
(1) **cell ratio** — every cell whose EN count ≥ 10 has translated ≥ 95 % of its EN count;
(2) **cell floor** — every such cell has ≥ 10 translated rows (one full session without repeats);
(3) **category floor** — every category has ≥ `min(30, ceil(0.95 × its eligible EN rows))` translated rows, because fallback rung 3 drops `difficulty` entirely (`:368-376`) and the category is then the real serving unit. This bar is **relative, not absolute**: a category with fewer than ~32 eligible EN rows cannot be blamed for a shortfall the English corpus creates, so it is reported `en_starved_category` and its bar degrades to "translate what exists". Without that escape one thin category would permanently block a whole language with no defined remedy.
Cells whose EN count is < 10 are already EN-starved: reported as `en_starved`, excluded from bars 1–2, never silently passed. Prod's `approved`-only population is binding; the TestFlight set (`:246-250`) is reported alongside but does not relax the bar. **On failure** the report exits non-zero listing every failing cell (`category, difficulty, en, translated, ratio`) and step 4 does not happen. Step 4 is evaluated **per language**, so SK can cut over while CS is still short.
*Remedy when a bar fails — two paths, both explicit.* (a) **Translate more:** the report prints each shortfall count plus the qids of the untranslated eligible EN rows, which is directly the next `translate_corpus.py submit --limit` work set. (b) **Founder-accepted waiver:** `report --coverage --language sk --waive <category>[/<difficulty>]="<reason>"` prints that bar as `WAIVED`, records it verbatim (bar, cell, reason, date) in the run-report JSON, and exits 0. Waivers are per run and never persisted as config, so the next run re-asks; an unwaived failure still exits non-zero. A waiver accepts a thin cell for the **whole language** — it does not create a per-category runtime gate, because that would need exactly the runtime fallback locked decision 2 forbids.
*The numbers are defaults, not measurements.* No (category × difficulty) crosstab exists today (recon §10), so 10 / 95 % / 30 are starting values derived from the retrieval shape, not from the corpus. They live as named constants (overridable CLI flags) in the runner; the **first** `report --coverage` run prints the full 18-cell crosstab of eligible EN rows and the founder confirms or adjusts the thresholds before any of them gates a cutover.

**DD13 — Blind answerability is a DELTA check: the same model answers the EN source as a control, and only EN-pass + target-fail counts as a translation defect.**
Without a control leg, a model that simply cannot answer a hard question is indistinguishable from a translation-induced answer flip and the false-reject rate is unbounded. For every `(question, language)` draft the checker runs **twice with identical settings in the same batch submission** — control on the EN source, treatment on the translated draft — and classifies the pair: `en_pass ∧ ¬tgt_pass` → `translation_flip`, **critical, blocks approval**; `¬en_pass` → `control_fail`: hard or ambiguous in English too, the translation is not blamed, the pair is logged for a corpus follow-up and never drops an EN-approved question; both pass or both fail → pass. Either leg returning `check_unavailable` (`answerability.py:151-155`) → `unavailable`: for a *gate* the fail-safe direction inverts, so the row stays `pending` rather than being approved on a missing judgment.
*Model class:* the existing answerability role (`deepseek-v4-flash`, `factory.py:160`) — cheap is the point, it proxies a player. But a control run in a language the model reads badly is worthless, so the arm test (DD8) carries a **competence pre-check**: run the delta check over ~20 human-approved SK (and CS) translations; if the flip rate on known-good translations exceeds 10 %, the role model is unusable for that language and the check moves to a frontier model with founder approval (standing rule: no model swaps without eval data). That measurement is what bounds the false-reject rate empirically instead of asserting it.
*Ordering — DD13 depends on DD8's output.* Those ~20 human-approved translations per language do not exist until the arm test has been rated and the founder verdict has picked a model per language, so the pre-check is **downstream of DD8**: it runs on the arm-test items the founder approved on the rating web (the winning arm's output, per language), after the model verdict and before any corpus batch is verified. DD13's answerability-model decision is therefore an output of DD8, not a parallel task. If a winning arm yields fewer than ~20 approved items in a language, the pre-check waits for the first verified corpus batch rather than running on a thin sample.
*Prompt shape:* `_PROMPT` (`:36-41`) verbatim in structure — question, optional `OPTIONS:` block, JSON-only `{answer, gave_up, issue}` — with the instruction text localized per language and the answer required in the target language. *Comparison:* MCQ compares the resolved **option key** (DD3 stores `correct_answer_key`), which removes most normalization risk; free text needs a Unicode-safe normalizer, because `_normalize` (`:51-56`) strips every non-`[a-z0-9]` character and would erase SK/CS diacritics — casefold + NFKD accent-aware compare, and `_ARTICLES` (`:34`) drops out for SK/CS.
*Persistence:* `question_translations.verification.answerability` (DD3) = `{model, en: {answer, passed, reason}, target: {answer, passed, reason}, verdict, checked_at}` — **both legs stored**, so a later re-tune can re-score without re-calling the model.

**DD16 — Exhaustion accounting is gated by the same language filter as serving, so a finished SK/CS pool ends the session with 409 `reset_history`, never a 500.**
`/start` counts the corpus **globally** when the retriever returns nothing: `question_retriever.count(filters={"review_status": "approved"})` (`quiz.py:124-126`) vs `client_seen_count = len(client_excluded_ids)` (`:127`); the graceful branch trips only at `client_seen_count >= total_count * 0.8` (`:129-138`), otherwise the request falls through to `HTTPException(500, "Database has N approved questions, but none match…")` (`:140-162`). The `review_status` part must mirror the session's channel, not a hardcoded `"approved"`, or a TestFlight session (`{$in: [approved, pending_review]}`, `:246-250`) hits the same class of mismatch in the other direction.
*Scope — only `/start` has this defect.* Mid-session exhaustion is already graceful: `flow.py:254-261` transitions to `FINISHED` with `quiz_finished=True` when the retriever returns `None`, so no change there.
